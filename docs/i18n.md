# Languages (i18n)

The mail app speaks Vietnamese, English and Simplified Chinese. English (`en`) is the source; `vi` and `zh-CN` are translations of it. The public landing pages are separate: they have their own text and are served per language at `/`, `/en/` and `/zh/` (see [pwa-and-push.md](pwa-and-push.md)).

There is no runtime dependency for this: a flat JSON file per language, a small `t()` function, and the browser's own `Intl`.

## Where things live

| Path                                            | What it is                                                                                                                                                                                                                                                                        |
| ----------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `src/shared/i18n/locales/en.json`               | The source catalogue. Flat keys (`area.item`), `{name}` placeholders, plurals as `key#one` and `key#other`                                                                                                                                                                        |
| `src/shared/i18n/locales/vi.json`, `zh-CN.json` | The translations, same keys                                                                                                                                                                                                                                                       |
| `src/shared/i18n/locales/server/*.json`         | The Worker's own texts (push notifications). The Worker imports only these, never the client catalogues                                                                                                                                                                           |
| `src/shared/i18n/glossary.json`                 | The agreed words (folder names, account and security terms) in all three languages                                                                                                                                                                                                |
| `src/shared/i18n/notes.json`                    | For every key that is not a glossary term: where it is shown (`context`), whether it is about security (`security`), and a hard length limit where the layout needs one (`max`, in columns: a letter is 1, a Chinese character 2, a {placeholder} 4). It is what translators read |
| `src/shared/i18n/languages.ts`                  | One row per language: its tag, its own name, the `?lang=` values and the browser languages that choose it. The types follow from it                                                                                                                                               |
| `src/shared/i18n/index.ts`, `core.ts`           | `t()`, `tDyn()`, `fmt`, the plural and placeholder logic, loading and switching                                                                                                                                                                                                   |
| `src/shared/i18n/families.ts`                   | The key families built at run time (`err.<code>`, `audit.action.<code>`, `activity.kind.<kind>`)                                                                                                                                                                                  |
| `src/client/lib/i18n.ts`                        | What the client imports: `useT`, `tr`, `tRich`, `fmt`, `initLanguage`, `chooseLanguage`                                                                                                                                                                                           |

## Which language the screen uses

In this order, the first that is set wins:

1. the signed-in person's saved language (Settings > Account > Language, kept on the server, so it follows them to every device);
2. `?lang=vi|en|zh` (or `zh-CN`) on the link, which is what the Sign in buttons of the landing pages carry. A link alone is never saved;
3. the choice made in the small language picker on the sign-in screens, kept on this device in `localStorage` under the key `lang`;
4. the browser's languages: `vi*` is Vietnamese, `zh*` is Simplified Chinese, `en*` is English;
5. the organisation's default language (set in Setup, changed by an admin in the admin console; `default_language` in `GET /api/auth/session`);
6. English.

The app resolves 2 to 4 before the first render and loads that language's catalogue first, so nothing flashes in the wrong language. When the session arrives, 1 and 5 take over. A person with no saved language who signs in after choosing one in the picker has that choice saved to the account once. `<html lang>` always follows the screen.

`en` is bundled with the app (it is the fallback for any missing key). `vi` and `zh-CN` are separate files that the browser fetches on demand and the service worker keeps. If one cannot be fetched (offline, never cached) the app starts in English instead of failing.

## Writing code with it

In a component, `t` is already the theme, so the translate function is called `tr`:

```tsx
import { useT } from '../lib/i18n';

const tr = useT(); // the component renders again when the language changes
<button aria-label={tr('compose.attach')}>{tr('action.send')}</button>;
tr('list.selected', { count }); // plural: needs list.selected#one and list.selected#other
```

Outside a component, in code that runs when called: `import { tr } from './i18n';`. Never translate when a module loads, and never keep translated text in a module-level constant: keep the key (`labelKey: 'folder.inbox'`) and translate where it is shown.

- Keys are typed: `tr('no.such.key')` does not compile.
- A numeric `count` parameter picks the plural form. English has `one` and `other`; Vietnamese and Chinese have `other` only.
- No HTML in a text. For a link or bold part use `tRich('key', { link: <a href="...">...</a> })` with a `{link}` slot in the text.
- Dates, times, relative times and numbers: `fmt.date`, `fmt.time`, `fmt.dateTime`, `fmt.relative`, `fmt.number`. Never `toLocaleString()` or `new Intl.DateTimeFormat()` in the client.
- API errors: the server answers `{ success: false, error, code }`. The client shows the catalogue's `err.<code>` (never the English `error`). Calls take a fallback key (`apiGet(url, 'fail.load_stats')`) for answers that carry no code.
- A text built from pieces cannot be translated (word order differs). Write one sentence with placeholders.
- "Edging Mail" and "Edgar" are never translated.

## Fixing a translation

Edit the value in `vi.json` or `zh-CN.json` (or the file of another language); keep the key and every `{placeholder}` exactly. There is nothing to generate or sync: these files are the catalogues the app reads. Follow `glossary.json` for the agreed words (a folder is "Hộp thư đến" / "收件箱" everywhere) and `notes.json` for where a text is shown and how long it may be. Then run `npm test`: it checks that all the files have the same keys, the same placeholders and the right plural forms, that the glossary words are used, that no text is longer than its limit, that every key has its note, and that the wording rules hold (a message is never a conversation; the recovery key and the recovery codes are never mixed; a button has no final full stop; and so on).

## Adding or changing a text

1. Add the key to `en.json` (`area.item`; `{name}` placeholders; plural forms as `key#one` and `key#other`) and show it with `tr('area.item')`. The compiler checks the key.
2. Add the same key to every other catalogue. If you cannot translate it, copy the English text as a stand-in: `npm test` lists stand-ins and does not fail on them; `I18N_REQUIRE_TRANSLATED=1 npm test` does (the release check).
3. Add its note to `notes.json`: `context` (where it is shown and what it means), `security` (`true` for anything about encryption, keys, recovery, two-factor, passwords or sign-in sessions: the test requires it for those), and `max` when the layout limits the length (buttons, chips, titles).
4. When you change the meaning of an English text that is already translated, change the other files in the same pull request, or say in the pull request that they are out of date.
5. A new error code in `src/worker/errors.ts` needs `err.<code>`, a new audit action `audit.action.<action>` and a new kind of sign-in history row `activity.kind.<kind>`, in every catalogue; a new notice kind needs its sentence in `describeNotice` (`src/client/lib/activity.ts`). A test names the one that is missing.

## Adding a language

There is no tool to run: the catalogues are plain files in the repository and `npm test` is the check. The example is French, tag `fr`.

1. **The list.** One row in `LANGUAGES` in `src/shared/i18n/languages.ts`: the tag, the language's own name, the `?lang=` values that choose it and the first part of the browser languages it covers: `{ tag: 'fr', name: 'Français', params: ['fr'], browser: ['fr'] }`. The pickers, `?lang=`, the browser match and the types all follow from this row.
2. **The catalogue.** `src/shared/i18n/locales/fr.json`: copy `en.json` and translate the values. Keep every key and every `{placeholder}`. The plural forms are the ones `Intl.PluralRules` gives for the language (English has `one` and `other`; Vietnamese and Chinese have `other` only), and the test asks for exactly those.
3. **The Worker's texts.** `src/shared/i18n/locales/server/fr.json`: copy `locales/server/en.json` and translate it.
4. **The glossary.** An `fr` column on every row of `src/shared/i18n/glossary.json` (the folder names and the security terms). `unchangedNames` stay as they are.
5. **The loader.** One line in `loaders` in `src/shared/i18n/index.ts`: `fr: () => import('./locales/fr.json')`. The compiler refuses to build until it is there.
6. **The Worker.** It validates and stores a person's language, and it reads the same list: `LANGUAGES` in `src/worker/auth/accounts.ts` is `LOCALES`, and the types follow from `Locale`, so a new row is accepted by `/api/settings`, Setup and the admin console and stored with no change to a route. The column `users.language` has no CHECK, so there is no migration either. What is left:
   - the server file in `CATALOGUES` of `src/worker/security.ts` (with its import), which is where push texts come from. It is typed `Record<Locale, …>`, so the compiler refuses to build until the file is there;
   - that is all. The three English sentences that list the languages (`invalid_language` in `src/worker/errors.ts`, the reasons in `src/worker/mail/settings.ts` and `src/worker/auth/setup.ts`) are built from `LOCALES`, so a new language appears in them by itself and nothing is left to edit there. Their text stays English (the client shows its own text for the code `invalid_language`); the error code is unchanged.
7. Run `npm run check` and `npm test`.

What the tests say if you forget something: a missing catalogue file, server file or glossary column is named in "the language list and the files"; `/api/settings refused fr` or `add the file to CATALOGUES` is the Worker part (`test/i18n/wiring.test.ts`); a key or placeholder that differs, a missing plural form or a text over its `max` is named with the key and the language. A copy of the English text counts as untranslated: it is listed, and `I18N_REQUIRE_TRANSLATED=1 npm test` fails until it is translated. The wording rules of the glossary that name words (what a conversation is called, how the recovery key is named) have one entry per language in `test/i18n/catalogue.test.ts`; a language with no entry is simply not checked by that rule, so add one when you know the words.

Two things are separate on purpose. The landing pages have their own list (`src/worker/site/languages.ts`), their own copy and a path of their own, so a new app language does not add a landing page. The READMEs are one file per language (`README.md` is the source, `README.vi.md` and `README.zh-CN.md` follow it) and each shows the screenshots of the app in its own language.

## The Worker's texts

Push notifications are written in the recipient's language: their saved language, else the organisation default. The texts are in `locales/server/*.json` (a subject or message body never goes into a push; only a sender line and security notices do). The notification's click URL is a fixed path, not part of the text. `public/sw.js` only falls back to the product name when a push carries no title.

## Tests

- `test/i18n/core.test.ts`: placeholders, plurals, fallback, the language list (every row can be chosen, no two rows share a value), the language order, formatters, the switch.
- `test/i18n/catalogue.test.ts`: a file and a glossary column for every language, key and placeholder parity, plural forms, glossary, wording rules, notes (every note has its key, every key its note, security flags), length limits, and the list of values that are still the English text. `I18N_REQUIRE_TRANSLATED=1 npm test` turns that list into a failure (the release check).
- `test/i18n/wiring.test.ts`: every language of the app can be saved by a person and its push texts come from its own file (the Worker side of "Adding a language").
- `test/i18n/errors.test.ts` and `test/static/error-codes.test.ts`: every error code has its `err.<code>` text. `test/static/history-words.test.ts` and `test/static/notice-kinds.test.ts`: every audit action, sign-in history kind and notice kind the Worker writes has its words. `test/static/json-keys.test.ts`: no catalogue file holds a key twice.
- `test/static/client.test.ts` and `usage.test.ts` (run under Node): every `tr('...')` key exists, every key is used, no hard-coded user-visible text in `src/client` (JSX text, `aria-label`, `title`, `placeholder`, `alt`, toasts, dialogs, sentences returned from helpers), no `toLocale*String` or `Intl` formatter with a locale of its own, no element found by a visible string. A text that is not for people (a developer error) goes in `test/static/helpers/allow.ts` with a reason.
